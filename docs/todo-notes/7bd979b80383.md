# Story 7bd979b80383 (C8) — `kb transfer --from memex <dir>` notes

Sprint #163. Everything in the story is implemented. Two points below are
faithful-to-the-story decisions with cross-story consequences worth flagging to
the kb integrator — neither is a narrowing of the story.

## 1. `Source.Tool = memex` vs. the agent-ring owner-scoped read (C1)

The story mandates `Source.Tool = memex` on every moved page, and that is what
the writer stamps. C1's agent ring (`pkg/kb/store.go`, outside this story's
Files list) scopes **reads** to the calling principal by `Source.Tool ==
ToolID()` (`OpenAgentRing` / `ownedBy`). Because moved pages are stamped
`memex`, not the moving principal's `ToolID()`, they are **not** returned by an
owner-scoped agent-ring read (`kb --ring agent search`) unless `ToolID()`
happens to be `memex`.

- The transfer itself is unaffected: it reads the ring **unscoped** (`Open`), so
  dedup and the idempotent second run work regardless of `Source.Tool`.
- Consequence for the feature's end goal (retire memex → the agent reads its
  memex knowledge from the ring): to surface these on the owner-scoped read
  path, C1's owner check would need to treat the agent-ring directory as
  owned-by-directory (matching the brief's "owner check is by principal name /
  `YCODE_DATA_DIR`"), or accept a transferred-in origin. That is a `store.go`
  change (C1's file), deliberately not made here.

## 2. memex `Scope` is not mapped onto `Page.Scope`

`Memory.Scope` is a memex **store location** (`global|project|team|user`);
`Page.Scope` is the kb **activation filter** (`{Repos, OS}`). They are different
axes, so the memex scope is intentionally not written into `Page.Scope` (which
would mislead the repo/OS activation filter). The field is still parsed (it is
part of the record shape) and the memory's original tags are preserved verbatim
alongside `xfer:memex`.
